# 수분수지 측정 파이프라인

## 목적과 범위

이 단계에서는 AI나 예측 모델을 사용하지 않는다. 수동 입력, 시뮬레이터, 실제 기기가
동일한 측정 계약을 사용하고, 같은 입력이면 같은 계산 결과가 나오는 구조를 만든다.

```text
수동 입력 ─┐
시뮬레이터 ├─> 표준 측정 계약 ─> 규칙 기반 수분수지 엔진 ─> 결과 + 경고 + 계산 추적 정보
실제 기기 ─┘             └─> 측정값·보정값·급수/배수 이벤트 저장
```

순수 계산 코드는 `backend/app/domain/water_balance.py`에 있고 HTTP, Supabase, 특정
로드셀에 의존하지 않는다. 입력 변환과 신뢰도 경고는
`backend/app/services/water_balance.py`가 담당한다.

## 표준 측정 계약

`POST /api/water-balance/evaluate`는 다음 정보를 받는다.

- `plant_id`: 측정 대상 식물
- `calibration`: 화분 세팅 무게, 충분히 젖은 목표 무게, 물주기 시작 무게, 보정 버전
- `start_measurement`, `end_measurement`: 시간대가 포함된 시각과 무게
- `source`: `manual`, `simulator`, `device` 중 하나
- `device_id`: 실제 기기 입력이면 필수
- `sequence_no`: 전송 중복과 누락을 찾기 위한 기기 측 순번
- `is_stable`: 흔들림이 사라진 안정 구간의 대표값인지 표시
- `raw_sensor_value`, `sample_count`: 로드셀 원시값과 평균에 사용한 샘플 수
- `water_added_ml`, `drainage_ml`: 해당 측정 구간의 누적 급수량과 배수량
- `environment`: 온도, 습도, 조도 또는 PPFD의 선택 입력

기존 `POST /api/water-balance`는 현재 모바일 수동 계산기를 위한 호환 API로 유지한다.
두 API 모두 동일한 순수 계산 엔진을 호출한다.

## 계산 구간과 보정값

화분을 처음 올렸을 때의 세팅 무게는 보정 이력으로 보관한다. 그러나 모든 계산을 설치 첫날부터
계속 누적하면 흙 유실, 식물 성장, 화분 이동 때문에 오차가 커진다. 실제 계산은 서로 짝이 맞는
`시작 안정 무게`와 `종료 안정 무게` 사이의 구간으로 수행하고, 그 구간 안에서 발생한 급수·배수
이벤트만 합산한다.

```text
수분 손실량 = (급수량 - 배수량) - (종료 무게 - 시작 무게)
하루 평균 손실량 = 수분 손실량 / 측정 구간 일수
현재 보충 필요량 = 충분히 젖은 목표 무게 - 현재 무게
```

무게 1g을 물 1mL로 근사한다. 결과는 식물이 흡수한 양만이 아니라 식물 증산과 흙 표면 증발을
합친 화분 시스템 전체의 물 손실이다. 물주기 기준 무게와 충분히 젖은 목표 무게는 사용자 관찰과
반복 실험으로 보정하며, 보정이 바뀔 때마다 버전을 올린다.

## 실제 기기 구현 규칙

로드셀 펌웨어 또는 기기 게이트웨이는 다음 규칙을 지킨다.

1. 기기 부팅 후 영점과 알려진 추로 스케일 계수를 확인한다.
2. 일정 시간 동안 연속 샘플을 모으고 중앙값 또는 절사평균으로 대표 무게를 만든다.
3. 최근 샘플의 범위나 표준편차가 허용 오차 이내일 때만 `is_stable=true`로 보낸다.
4. 모든 전송에 UTC 시각, `device_id`, 증가하는 `sequence_no`, 펌웨어 버전을 남긴다.
5. 네트워크가 끊기면 로컬 큐에 저장하고, 복구 후 같은 순번으로 재전송한다.
6. 기기 비밀키는 펌웨어 저장소나 앱 번들에 커밋하지 않는다.

현재 평가 API는 로그인 사용자의 Bearer 토큰을 사용한다. 실제 무인 기기가 직접 서버로
전송할 때는 별도의 기기 등록 및 키 교환 API가 필요하다. 그 전까지는 모바일 앱이나 로컬
게이트웨이가 로그인 토큰을 보유하고 기기 데이터를 중계한다.

## 단계별 검증 계획

### 1. 시뮬레이터

`scripts/simulate-water-device.ps1`로 표준 JSON과 API 응답을 확인한다. 같은 측정값을 기존
수동 API와 새 평가 API에 넣었을 때 핵심 계산값이 같아야 한다.

### 2. 추 분동 벤치 테스트

- 빈 플랫폼에서 영점 오차를 측정한다.
- 알려진 무게를 여러 구간으로 올려 정확도와 선형성을 확인한다.
- 같은 무게를 반복해서 올려 반복성과 표준편차를 기록한다.
- 1시간 이상 같은 무게를 두어 영점 드리프트와 온도 영향을 확인한다.

### 3. 화분 테스트

- 충분히 관수하고 배수가 끝난 시점의 안정 무게를 목표 무게로 기록한다.
- 매일 같은 시간대에 안정 무게를 기록해 자연 감소 곡선을 확인한다.
- 급수 전후 무게와 실제 투입량, 배수량이 물수지 식과 맞는지 비교한다.
- 화분을 들거나 옮긴 구간은 불안정 데이터로 표시해 계산에서 제외한다.

### 4. 합격 기준 예시

초기 시제품 기준은 팀이 조정하되, 먼저 다음을 기록 가능한 지표로 둔다.

- 알려진 추 대비 평균 절대 오차
- 같은 추 반복 측정의 표준편차
- 24시간 영점 드리프트
- 패킷 누락·중복률
- 급수 전후 물수지 잔차

모델은 이 파이프라인에서 충분한 실제 로그와 정답 기준이 쌓인 뒤, 손실량 추정이나 임계값
보정을 교체하는 선택 모듈로 추가한다. 측정 계약과 원시 로그는 모델이 바뀌어도 유지한다.

## 저장 구조

`supabase/migrations/202610250001_water_measurement_pipeline.sql`은 다음 테이블을 정의한다.

- `measurement_devices`: 기기 소유자, 하드웨어와 펌웨어 버전, 마지막 접속 시각
- `plant_water_calibrations`: 식물별 보정값과 버전 이력
- `weight_measurements`: 정규화 무게, 원시 센서값, 안정 여부, 환경값
- `care_events`: 급수·배수·보정·세팅 변경 이벤트

PlanTalk 원격 Supabase 프로젝트에는 2026-10-27 적용했다. 모바일은 RLS가 적용된 사용자
세션으로 식물·활성 보정값·수동 무게·급수/배수 이벤트를 읽고 쓴다. 활성 보정값 교체는
`save_plant_water_calibration` 함수가 식물 행을 잠근 뒤 기존 값을 비활성화하고 버전을 올려
트랜잭션 하나로 처리한다.
